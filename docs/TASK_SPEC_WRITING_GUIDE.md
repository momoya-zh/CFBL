# 阶段任务书撰写规范（作者角色专用）

**适用角色：** 任务书作者
**版本：** V1.0
**日期：** 2026-11-13
**上位依据：** `docs/PROJECT_MASTER_SPEC.md` §11（多智能体协作）、§13（质量管理）

---

## 一、作者角色的边界

作者**只写文档，不写代码，不做审查**。

| 可以做 | 不可以做 |
|---|---|
| 写 `docs/PHASE_XX_TASK_SPEC.md` | 写 `src/`、`scripts/`、`configs/` 下的实现代码 |
| 写 `docs/*_PROTOCOL.md` 等规范 | 跑训练、跑验收测试脚本 |
| 做**一次性探针**以确定数值口径（如显存、吞吐、maxdiff） | 把探针脚本落地为项目文件 |
| 解释任务书条款的含义 | 判定实现"通过"或"不通过" |
| 出任务书修订版（V1.1） | 在争议中充当仲裁（那是项目负责人的权力） |

**探针的唯一用途是给任务书提供"实测依据"。** 探针结果必须标注测量条件（设备、输入、重复次数），并写清"这是给实现者的判断基准，不是验收结论"。

---

## 二、任务书的标准骨架

每份阶段任务书应包含以下 11 个部分，缺项须说明理由：

| # | 章节 | 必须回答的问题 |
|---|---|---|
| 0 | 本文档的效力 | 冲突时谁优先？哪些数值是冻结的？作者/实现者/审查者分别是谁？ |
| 1 | 阶段目标 | 只做哪一件事？交付物清单编号化；**明确列出"本阶段不做"** |
| 2 | 冻结协议 | 所有不可在实施中改动的数值、口径、库、顺序，逐条列表 |
| 3 | 模块与文件清单 | 新增哪些文件（含关键接口签名）、修改哪些文件、**禁止改动哪些** |
| 4 | 主循环/流程伪代码 | 实现必须等价于什么 |
| 5 | 测试清单 | 编号化用例表，每行有**可判定的判定标准** |
| 6 | 时间与里程碑 | 含**硬性门禁**（哪个里程碑不过就不许往下） |
| 7 | 与总书的冲突说明 | 逐条列原文、本阶段处理、理由 |
| 8 | 风险与应对 | 含"禁止的应对方式"（如 OOM 时不许偷偷降 batch） |
| 9 | 验收标准 | 关闭条件，逐条可勾选 |
| 10 | 给实现 Agent 的执行顺序 | 明确"先提交设计、等确认再写代码" |
| 11 | 角色隔离与交接规范 | 启动包放什么、**不放什么**、冲突怎么升级 |

## 三、撰写时的硬性要求

### 3.1 数值必须可追溯

任何写进任务书的性能/精度数值，必须注明来源：

- **已实测** —— 附测量条件（设备、输入尺寸、重复次数、是否预热）
- **推算** —— 附推算公式与输入
- **冻结选择** —— 附选择理由，且理由不能是"惯例如此"

反例（禁止）：`batch size 设为 16。`
正例：`Batch 16：实测 SRCNN ×2 在 128 patch 下峰值显存 271.9 MiB（6 GiB 的 4.4%），吞吐 561 img/s，故选 16 而非受显存约束。`

### 3.2 测试用例必须有判别力

每个测试用例的"判定"列必须能**区分对错**，不能只写"通过"。

反例（禁止）：`测试插值输出正确`
正例：`downsample_bicubic 与 PIL.Image.resize 逐像素相等，maxdiff = 0` + `与 cv2.INTER_CUBIC 不相等，maxdiff > 0`（反例守卫）

**每个阶段至少含 1 组变异测试**：故意改坏实现，断言测试必须变红。这是本项目在阶段 3、阶段 4 各抓到一次零判别力缺陷后确立的固定回归项。

### 3.3 必须写"不做"清单

任务书不写边界，实现者就会扩边。每个阶段都要有明确的**越界即失败**清单（总书 §11.2 第 10 条：不进入未经批准的下一阶段）。

### 3.4 冻结项与可调项必须分开

- **冻结项**（协议、超参、口径）：改动须出 V1.1 并说明理由。
- **可调项**（如 `num_workers`、日志格式）：实现者可自行决定，但须记录。

### 3.5 与总书冲突时先写冲突表

总书 §17 末段：发现冲突须先提交冲突说明，不得自行覆盖。冲突表格式见 `docs/PHASE_05_TASK_SPEC.md` 第七章。

## 四、交接流程（作者视角）

```text
1. 作者：读总书 + 现有代码 + 上一阶段审查报告
2. 作者：做必要的一次性探针（不落地脚本）
3. 作者：出任务书 V1.0（本规范第二章骨架）
4. 作者：把"启动包清单"（任务书 §11.3）交给项目负责人
5. 负责人：新开【实现会话】，只注入启动包
6. 实现会话：提交设计确认 → 作者只看"是否满足书面要求"，不评价实现
7. 实现会话：实现 + 自测 + 阶段报告
8. 负责人：新开【审查会话】，只注入任务书 + 实现产物
9. 审查会话：出 PHASE_XX_REVIEW.md
10. 负责人：裁定 → 通过则关闭阶段；不通过则由实现会话修复 → 新开【复审会话】
```

**关键纪律：**

- 第 5 步和第 8 步必须是**全新会话**，不得复用作者会话。
- 实现会话与审查会话之间**不得**有任何对话往来，只能通过文件。
- 复审必须**再开一个新会话**，不能沿用第一次审查的上下文（否则复审会继承第一次的盲区）。
